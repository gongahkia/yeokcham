# ADR-040 — Local device identities without implicit authority

- Status: Proposed
- Date: 2026-08-06
- Deciders: maintainer
- Supersedes: None
- Superseded by: None

## Context and problem statement

M10-03 follows ADR-039. `Ref_event_v1` proves only that a caller-supplied
public key signed exact proposal bytes. It deliberately has no device claim,
key lifecycle, or private-key storage. Local synchronisation now needs a
stable, inspectable public device declaration without inferring identity from a
hostname, account, network address, clock, or other host metadata.

Current milestone: M10 Local Synchronisation. Vertical slice: generate an
opaque local device ID and Ed25519 keypair, persist only one public immutable
device declaration, and resolve a verified ref-event signer to an explicit
caller-supplied device registry. It excludes private-key persistence,
transport, automatic trust, ref mutation/reconciliation, labels, device
discovery, multi-device user accounts, key rotation/revocation, recovery,
encryption, consensus, background sync, and CLI. No implementation begins
before this ADR is accepted.

## Decision drivers

- Preserve ADR-020 create-only immutable publication and ADR-039 exact signer
  key IDs and verification semantics.
- Keep a long-lived device identifier distinct from a signing key, event ID,
  stored-object ID, mutable ref, and person/account identity.
- Keep private key bytes outside Paengi's object store until a dedicated local
  secret-storage decision exists.
- Make registry ambiguity, corrupt declarations, absent mappings, and entropy
  failure explicit before any repository state changes.
- Retain no host-derived or user-identifying data in shared device objects.

## Considered options

### Derive a device identity from host metadata

- Needs no new persistent object.
- Hostnames, usernames, hardware identifiers, addresses, and clocks are
  mutable, private, non-portable, and cannot establish authority.

### Treat each signer key as the device identity

- Reuses ADR-039's key ID.
- Cannot preserve a device identity across an eventual key rotation and makes
  a cryptographic key an unqualified person/device claim.

### Store private keys in the repository

- Makes restart signing convenient.
- Adds plaintext-secret, backup, encryption, permission, recovery, and
  cross-device disclosure policy before those boundaries are defined.

### Store an immutable public declaration with an injected signing capability

- Separates random device identity, public key declaration, signing capability,
  trust, and later lifecycle policy.
- Requires an explicit caller to retain or re-provide private material after a
  restart.

## Decision outcome

Select an immutable public declaration with an injected signing capability.

`Device_identity_v1` is a new immutable Envelope object type. Its canonical
Profile-1 payload is:

```text
device-identity-v1 = [
  1, device-id, signer-key-id, signing-algorithm, signing-public-key,
  mandatory-features
]
```

`device-id` is exactly 32 opaque random bytes, rendered only as lowercase hex
when inspected. It is generated by a small entropy adapter backed by an
explicitly initialised OS CSPRNG; entropy initialisation or generation failure
is a structured error. The functional core instead accepts exact device-ID and
Ed25519 key values, so generated tests can inject deterministic bytes without
making them production identity material.

V1 accepts only `signing-algorithm = "ed25519"`, a 32-byte public key, and the
existing ADR-039 32-byte `signer-key-id = SHA-256("paengi:ref-key:v1\000" ||
public-key)`. `mandatory-features` uses ADR-019 canonical ordering and unknown
mandatory features reject. A declaration is public and has no self-signature:
it is a precise key-to-random-device association, not proof of authority,
ownership, personhood, or trust.

The generation adapter returns the private Ed25519 capability only to its
caller. Paengi serialises neither that capability nor its seed, bytes, key
locator, recovery phrase, passphrase, or operating-system keychain reference.
The persistent store accepts only the public declaration through ADR-020
create-only publication. Restart can reload and validate public declarations,
but signing again requires the caller to re-provide a capability; absence is a
structured unsupported/unavailable result, not a replacement key or identity.

A device registry is transient caller input of at most 256 validated public
declarations, each paired with its exact `Stored_object_id`. Given an
ADR-039-verified event, pure resolution returns exactly one of:

```text
Device_resolved(device-id, stored-object-id)
Device_unmapped(signer-key-id)
Device_ambiguous(signer-key-id | device-id)
```

Registry rows are canonically sorted by `(raw device ID, raw stored-object ID)`;
an exact duplicate row rejects. The same signer key in more than one row, or
more than one record for a device ID, is `Device_ambiguous`; a malformed,
wrong-type, wrong-ID, or mismatched key-ID row is a structured rejection.
Resolution does not change an event's
`Verified`/`Untrusted` result, make a key trusted, change a ref, or select a
divergent proposal. A ref event remains `Untrusted` unless ADR-039's separate
caller-supplied key map verifies it, even when a matching device declaration
exists.

V1 records exactly one signing key per declaration. It has no rotation,
revocation, expiry, recovery, delegation, aliases, or user/device grouping. A
caller may stop supplying a declaration in a transient registry, but that does
not delete an immutable object, revoke a key cryptographically, alter old event
verification, or infer a replacement. A future lifecycle ADR must define any
rotation/revocation record, delegation proof, selection policy, retained v1
decoder/fixture behaviour, and explicit treatment of concurrent declarations.

The declaration contains no label, hostname, username, account, address,
hardware identifier, locale, timestamp, transport data, or private key. A
future local-only UI label must remain outside canonical/shared bytes unless a
separate privacy decision says otherwise.

## Consequences

- A device declaration is inspectable and portable as an immutable public
  object, but it establishes no authorisation or human/device identity claim.
- Ref-event bytes and verification remain unchanged; resolution is a separate
  observation after successful ADR-039 verification.
- Public-device reload works without exposing a private key, while restart
  signing needs explicit caller-owned secret handling.
- Rotation and revocation are deliberately unavailable rather than implicit or
  last-writer-wins registry updates.

## Model and invariant impact

New values are `Device_id`, `Device_identity`, `Device_registry`, signing
capability, entropy source, and device-resolution result. They are distinct
from signer-key ID, ref-event ID, stored-object ID, mutable ref, release
attestation, checkpoint, capsule, revision, workspace, conflict, and release.

- One valid declaration has one exact canonical public payload and one typed
  stored-object ID.
- A device ID is exactly 32 random opaque bytes; no host-derived field enters
  its canonical representation.
- The declaration's public key and signer-key ID must recompute exactly.
- A registry maps a verified signer key to at most one device declaration;
  absence and ambiguity remain explicit outcomes.
- Generation, store/load, resolution, transfer, and every failure leave
  mutable refs unchanged.

## Persistent-format and migration impact

After acceptance, `Device_identity_v1` receives new Envelope type code 27 and
retained canonical goldens. It is additive: existing Envelope, repository
format, ADR-020 object IDs, mutable refs, exchange-v1 frames, and
`Ref_event_v1` bytes remain unchanged. Existing repositories contain no device
declarations and need no migration. An unknown mandatory feature, wrong
version, or malformed declaration rejects before publication or resolution.

A later device format or lifecycle object keeps the v1 decoder and fixtures or
rejects v1 before use; it never rewrites a device declaration, ref event, or
mutable ref in place.

## Verification

Required after acceptance:

- Exact declaration/store Envelope goldens and inverse canonical decoders,
  including retained ref-event-v1 and prior persistent fixtures.
- Focused generation, key-ID recomputation, public-only persistence, reload,
  malformed/corrupt/unknown-feature/type/version/key/ID/registry-bound
  rejection, and no-private-bytes-in-payload tests.
- Two-local-device fixtures: independently generated declarations transfer and
  reload; a verified event resolves only through one explicit registry; absent
  and ambiguous rows are explicit; every ref remains unchanged.
- Bounded seeded state-machine/restart/failure properties varying device IDs,
  signer keys, duplicate/corrupt records, missing/ambiguous registry rows, and
  repeated create-only publication.
- `make check`, `make property-test PROPERTY_TEST_SEED=17`, and failure tests
  for entropy and persistent-publication interruptions.

## CLI and user impact

No CLI, device discovery, trust configuration, ref application, or private-key
storage is added in M10-03. A future inspector may report an exact public
device declaration or explicit mapping outcome; it must not state that a
person/device is trusted, identified, reachable, authorised, rotated, revoked,
or synchronised.

## Implementation evidence

None; implementation is blocked pending ADR acceptance.
