# M1b.2 private recovery contract

**QUALIFIED_FOR_M1B2_IMPLEMENTATION** for the existing M1b.1 runtime profile.

The checkout starts at `1d75d7f1d6c666ea1474ceca4e33363068d4f444` with the
M1b.1 report untracked. The [M1b.1 contract](M1B1_STORAGE_CONTRACT.md) fixes
schema version 1, application ID `0x594b5031`, the FORMAT bytes, the
`yeokcham/private-request/m1b1\0` digest domain and the SQL transaction order.
This tranche consumes those bytes unchanged. Schema migration and a new
authority are unnecessary. The adapter can check associations already present
in the five tables. See the [D3 ownership and transaction rules](../D3_CONTRACT_FREEZE.md)
and [D4 object and SQLite boundaries](../D4_BLOCKER_RESOLUTION.md).

## Recovery boundaries

| Boundary | Durable authority on recovery | Physical possibilities and retry |
| --- | --- | --- |
| New key, validation and pending request/root INSERTs before COMMIT | No request or new root until both commit | SQL recovery rolls back the whole claim or recovers the whole pair. Reuse the exact key/arguments. Never infer a claim from a stage or object filename. |
| Pending claim committed, before/during staging | Pending request with its exact snapshot root, old cursor | Missing objects, partial exclusive temp files, or existing canonical bytes are possible. Reuse exact inputs and verify or publish each dependency. |
| After staging file fsync, before canonical hardlink | Same pending owner | A staged file may exist. Retry uses a new exclusive temp. No reuse or cleanup of unowned temp names. |
| After hardlink, before object directory fsync or cleanup sync | Same pending owner | Canonical bytes can be readable even if their durability is unknown. Retry verifies exact bytes using the existing file descriptor and re-establishes file and object-directory sync. |
| Complete closure, before final COMMIT | Same pending owner and old cursor | Even verified complete bytes confer no capture identity. Revalidate original intent, root, cursor, and version. Final capture/cursor/completion changes are atomic. |
| Final transaction failed or process died | Pending or completed, as recovered by SQLite | A pre-COMMIT failure attempts rollback. COMMIT errors yield UncertainCommit even if rollback appears to succeed. Resolve by original key using a fresh connection after recovery. |
| Final COMMIT succeeded, response lost | Completed request, immutable capture and root | Reverify historical bytes, return the same result. An unchanged request references the existing capture. No repeated sequence allocation. |
| Completed, object later missing or invalid | Completed metadata with unavailable or invalid closure | Retain original capture and all roots. Report absence or validation error and refuse replay or affected reads. Never represent a missing file as empty. |
| Canonical object with no owning request | No capture or request inferred | Preserve the object. It may be used only by future exact, reverified publication. |

A stale pending request retains its original key, digest, root and expected
workspace. It cannot resume with later arguments or a newer cursor. An
unrelated workspace may proceed because only the affected workspace's write
lock is held across object work. SQLite connections and metadata leases close
before object traversal. The shared publication lease protects the complete
read or publication. Ordinary readers keep shared metadata leases. Exclusive
admission remains confined to reopen and physical DB header checks. A
separate database inspector runs in a fresh process after fault recovery.
Unknown stores are refused before recovery writes. A missing or malformed
FORMAT marker on an incomplete initializer cannot be regenerated by inspection.

## Typed inspection

`inspect_request(workspace, key)` returns `None` for a key absent in a
successful recovered SQL read. Otherwise it returns `RecoveryInfo` with the
original `RequestInfo`, argument digest, expected `WorkspaceState` and
`eligible: bool | None`. Eligibility compares the expected and observed
workspace at the metadata read boundary. It is `None` for completed metadata.
The closure field has four values:

- `verified` means a complete validation pass over the exact snapshot
  closure. It gives no evidence about sync, COMMIT or future availability.
- `missing` means an encountered required canonical object was unavailable.
- `invalid` means an encountered envelope, identity, content, representation
  or format check refused. The content error code is retained.
- `unverified` means a resource limit or I/O failure stopped verification.
  The relevant content or storage error code is retained.

The traversal reports the first refusal and does not certify all other objects
after one failure. Pending/complete metadata and eligibility are independent of
closure state. Inspection copies SQL facts in one short read snapshot under
the publication lease, closes the SQL connection, then verifies objects. It
can observe progress from a concurrent publisher and grants no authority for
a later retry. It never calls a resolver outside the store, syncs object
bytes, completes a request, advances a cursor, or releases a root.
Known-format SQLite journal recovery remains part of reopening. If metadata
cannot be read, inspection raises the typed store error. A failed read is
neither an absent key nor a persisted Uncertain state.

`lookup_request`, `append_capture`, `read_snapshot`, and `verify_roots`
retain their shapes and prior meanings. The aggregate root audit is not a
substitute for per-key inspection. Open validates SQLite integrity and FKs plus
the linear schema's logical capture ancestry, original producer and completion
links. A known key must have the matching root and frozen digest. The final
transaction must still see that pending row and complete exactly one request.
No adapter may reconstruct a row from physical files.

## Error handling and exclusions

Rollback is attempted only for a live transaction. Rollback and close errors
are secondary to the primary failure and must remain inspectable as exception
notes. If COMMIT was attempted and returned an error, report UncertainCommit.
A transaction-body failure does not imply completion. Close the connection
before retry. No retry silently changes the key, arguments, or closure.

A live put may clean up its own exclusive inode if it still owns the name.
Unlink or directory-sync failure refuses publication success, preserves
canonical bytes, and leaves the exact request eligible only for verified
retry. When publication also failed, that primary error takes precedence and
cleanup errors are reported as secondary. A replaced stage name is preserved.
No generic stage walk, automatic abandonment, expiry, GC, backup, worktree
action, or recovery journal is introduced.

Incomplete and stale pending roots can block future reclamation indefinitely.
Neither observed completeness nor staleness is authority to release a root.
This contract qualifies the logical state machine for implementation.
Runtime verification must record the exact faults reached, independent row
and byte inspection, and concurrency outcomes. Process crashes and injected
syscall failures provide no physical power-loss or storage-controller evidence.

## Directory-sync refusal during retry

The installed SQLite VFS can report `SQLITE_IOERR_DIR_FSYNC` after removing
the rollback journal. A fresh SQL read may then see a committed row. For a
write or replay using an existing key, sync the store directory after reading
that row and closing the metadata connection. A failed sync yields
`UncertainCommit`, before object production or a completed acknowledgement.
This also covers a pending claim recovered after an uncertain claim COMMIT.
Read-only inspection reports the SQL state it observed without asserting that
a previous failing directory sync has been repaired.
